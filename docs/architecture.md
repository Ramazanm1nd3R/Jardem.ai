# Архитектура Jardem.ai

## Кластер

Вся платформа поднимается одной командой (`docker compose up`) и доступна с одного адреса.

```
                          ┌──────────────── gateway (nginx) :8080 ────────────────┐
  браузер / телефон  ───► │  /               сайт (React, web/dist)               │
                          │  /app/citizen/   приложение гражданина (Flutter web)  │
                          │  /app/responder/ приложение экипажа (Flutter web)     │
                          │  /api/…  /api/v1/ws   ──────────────► backend :8000   │
                          └───────────────────────────────────────────────────────┘
                                                                      │
                                   ┌──────────────────────────────────┼──────────────────┐
                                   ▼                                  ▼                  │
                        db: PostgreSQL 16 + PostGIS         redis: pub/sub событий       │
                        каталог, вызовы, аудит, треки       для WebSocket-клиентов       │
```

| Сервис | Роль |
|---|---|
| `gateway` | Единая точка входа: статика сайта и двух приложений, прокси API и WebSocket |
| `backend` | FastAPI: REST + WebSocket, движок диспетчеризации, симулятор |
| `db` | Справочник подразделений и экипажей (география в PostGIS), записи вызовов с хронологией, журнал событий, треки экипажей; поиск ближайших подразделений — KNN-запрос PostGIS |
| `redis` | Канал `jardem:events`: backend публикует события, подписчик раздаёт их WebSocket-клиентам |

Живое состояние (где какой экипаж, маршруты, открытые вызовы) backend держит в памяти одного процесса; в БД оно пишется по событиям. Поэтому backend запускается в одном экземпляре. При перезапуске история вызовов сохраняется, а незакрытые вызовы закрываются как отменённые — маршруты «в полёте» не восстанавливаются. Это осознанное упрощение прототипа.

## Код backend


## Маршрутизация

- Граф строится из OSM: вершины — перекрёстки, рёбра — участки дорог с длиной, классом, скоростью и геометрией.
- Время проезда ребра = длина / (скорость свободного потока × коэффициент пробки).
- Маршрут — A* по времени. Эвристика — расстояние в плоской проекции, делённое на максимальную скорость в сети; проекция сжата по долготе так, что расстояние не завышается, поэтому эвристика допустима и маршрут оптимален (проверяется сравнением с Дейкстрой на случайных графах).
- Для подбора экипажа нужен не один маршрут, а время от *всех* экипажей до точки вызова. Это один проход Дейкстры по обратному графу от точки вызова; дерево кэшируется по (узел, версия дорожной обстановки).
- Профиль `emergency`: экипаж со спецсигналами теряет в заторе 55% того, что теряет обычный поток, и едет на 15% быстрее свободного потока. Перекрытая дорога закрыта для всех.

## Пробки

Коэффициент ребра (доля скорости свободного потока) складывается из:

1. суточного профиля — утренний и вечерний пики, слабее днём; магистрали теряют до 60%, дворовые проезды до 5%; у каждого ребра своя детерминированная «восприимчивость»;
2. очагов — круг с убывающей к краю потерей скорости и временем жизни;
3. перекрытий — список рёбер, проезд запрещён;
4. проб — скорость, которую передало приложение экипажа; свежая проба замещает модель на своём ребре и затухает за 10 минут.

Уровни для карты: свободно ≥ 0,75 · замедление ≥ 0,5 · пробка ≥ 0,25 · затор < 0,25 · перекрыто. Экипажи в пути перестраивают маршрут, когда меняется дорожная обстановка, и сразу — если закрыто ребро впереди.

Это симуляция. Для реальной эксплуатации нужен лицензированный поток дорожных скоростей; модуль заменяется за интерфейсом `TrafficModel.edge_costs`.

## Оптимизатор назначений

Три стратегии с одним интерфейсом:

| Стратегия | Правило |
|---|---|
| `nearest` | по очереди приоритета каждый вызов берёт ближайший по прямой подходящий экипаж |
| `min_eta` | то же, но по времени в пути с учётом пробок |
| `jardem` | одна задача о назначениях на все открытые вызовы сразу |

`jardem` минимизирует

```
Σ x_ij · ( w(p_j) · T_ij  +  λ · C_i  +  π · O_ij  −  S_ij )  +  Σ (незанятые слоты) μ · w(p_j)
```

- `T_ij` — время в пути экипажа i до вызова j;
- `w(p)` — вес приоритета: критический 4, высокий 2,5, средний 1,5, низкий 1;
- `C_i` — потеря покрытия: на сколько секунд вырастет средневзвешенное по районам время доезда ближайшего свободного экипажа этой службы, если i уедет (λ = 0,6);
- `O_ij` — число редких возможностей экипажа, которые вызову не нужны (реанимация, педиатрия, спецотряд…), π = 120 с;
- `S_ij` — «липкость»: экипаж, уже едущий на этот вызов, получает скидку `w · max(90 с, 25% T)`, поэтому перенаправление происходит только при ощутимом выигрыше; после одного перенаправления экипаж фиксируется;
- μ = 5400 с — цена оставить слот без экипажа.

Для критических вызовов штрафы `λ·C` и `π·O` не применяются: при угрозе жизни едет самый быстрый экипаж, резерв и специализация берегутся только на менее срочных вызовах. (Первая версия применяла штрафы ко всем вызовам; эксперимент показал, что при малой нагрузке это замедляло прибытие на критические вызовы примерно на 30 с, и правило было изменено.)

Ограничения: совпадение службы, экипаж обладает всеми требуемыми возможностями, один экипаж — один слот, вызову нужно `units_required` экипажей (пожар — 2). Задача решается венгерским алгоритмом (собственная реализация, сверена с перебором и `scipy.optimize.linear_sum_assignment`).

Потеря покрытия считается для каждого экипажа отдельно (маргинально) — взаимное влияние нескольких одновременных назначений не учитывается; это приближение.

Веса — исследовательские параметры модели. В реальной эксплуатации приоритеты и штрафы задаются регламентами служб.

Результаты сравнения стратегий — в `docs/experiments/results.md`.

## Разбор обращения

`triage.py` — правила по основам слов на русском и казахском: служба, категория, срочность, признаки угрозы жизни и людей внутри, возраст, число пострадавших, адрес. Возвращает найденные основания (`matched`), недостающие сведения (`missing`) и другие затронутые службы (`also`). Текст может только повысить срочность. Это подсказка оператору, не решение.

LLM-разбор, голосовой ввод и RAG-помощник первой помощи в прототип не вошли.

## Роли и безопасность

Вход упрощён: гражданин — по номеру телефона без SMS-кода, экипаж и диспетчер — по общему PIN из конфигурации. Этого достаточно, чтобы разделить роли в демо; для пилота нужны SMS/eGov-идентификация и ведомственный SSO. Гражданин видит только свои вызовы; экипаж — вызовы, на которые назначен.

По умолчанию назначения выполняются автоматически (демо). Режим с подтверждением диспетчером включается через `POST /dispatch/settings {"auto_dispatch": false}`: оптимизатор только предлагает, назначает оператор.
